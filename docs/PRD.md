# SECOD Product Requirements Document

**Product:** SECOD — Security Coding Skills for AI Builders
**Status:** Draft v0.2
**Release:** SECOD v0.1.0-beta.1 public prerelease; v1.0.0 stable target
**Last updated:** 2026-09-04
**Owner:** iamruzaini / SECOD maintainers

## 1. Executive summary

SECOD is an open-source security skill library for people building applications with AI coding agents. It gives Codex, Claude Code, Cursor, and compatible agents practical security instructions, provider-specific implementation guidance, and evidence-based pre-launch reviews.

The standalone [`iamruzaini/secod`](https://github.com/iamruzaini/secod) GitHub repository is the canonical product. The separately maintained SECOD website imports immutable tagged releases for discovery, education, installation, and sponsor surfaces.

SECOD v1.0 launches as a complete 57-skill pack. It separates a general app-security baseline from conditional framework and provider adapters, so every reviewed application gets portable security coverage while stack-specific controls are applied only when detected.

## 2. Problem

Vibe coders can produce working applications quickly, but often ship avoidable security gaps:

- Privileged keys exposed in browser code or committed to Git.
- Authentication implemented without authorization or tenant isolation.
- Supabase, Firebase, storage, database, and cloud policies left open by default.
- APIs, webhooks, file uploads, redirects, and user input trusted without validation.
- Dependencies installed without verification.
- Payments, subscriptions, webhooks, and AI API integrations trusted without server-side evidence, limits, or reconciliation.
- A launch declared "safe" despite missing evidence.

Existing security resources are often too fragmented, too enterprise-focused, or too technical for a beginner. Vibe coders need a plain-language guide that their AI coding agent can also follow precisely.

## 3. Product vision

> Make secure-by-default AI-built applications as easy to start as installing a skill pack.

SECOD should feel simple to a human and rigorous to an AI agent:

- A human chooses their AI tool and stack, copies a command, and receives clear findings.
- The agent receives concise procedural instructions, conditional provider references, deterministic checks when useful, and a strict evidence standard.
- SECOD never claims a control is safe without verifying it.

## 4. Goals

### Product goals

1. Publish a complete, open-source v1.0 library with 57 installable skills: 19 general app-security baseline skills and 38 conditional framework and provider adapters.
2. Support Codex, Claude Code, Cursor, and other Agent Skills-compatible tools.
3. Support Clerk, Auth0, Better Auth, WorkOS, Supabase, Firebase, Neon, Convex, AWS and Google Cloud at launch.
4. Let a non-technical builder install either the full pack or a stack-specific subset from the SECOD website.
5. Provide a repeatable `secod-ship-check` outcome before a project is launched.
6. Make sponsorship commercially viable without allowing sponsors to influence security guidance.

### Quality goals

1. Base security guidance on official provider documentation and versioned security references, including OWASP ASVS 5.0.0 and OWASP API Security Top 10 2023; cite ASVS requirements using version-qualified identifiers such as `v5.0.0-1.2.5`.
2. Keep every skill focused, portable, and small enough to load reliably.
3. Treat unverified controls explicitly as "Not verified" rather than passing them.
4. Validate behavior using realistic insecure fixtures, not only happy-path examples.
5. Keep secrets, credentials, sponsor copy, and marketing content out of agent security instructions.
6. Keep the guided installer, catalog, Skill Contract Matrix and `secod-ship-check` dependency graph synchronized so a framework/provider adapter can never be installed or evaluated without its required baseline owners.

## 5. Non-goals for v1.0

- Hosting or operating a managed security scanner service.
- Replacing a professional penetration test, legal/privacy advice, or cloud security review.
- Certifying projects as compliant with SOC 2, HIPAA, PCI DSS, GDPR, or any standard.
- Automatically deploying changes to production without user approval.
- Providing a hosted secrets manager, SIEM, WAF, or vulnerability database.
- Supporting every framework, cloud provider, or programming language on day one.

## 7. Core user journeys

### 7.1 Full-pack installation

1. User visits `secod.dev`.
2. User selects **Install the full SECOD Pack**.
3. Website asks which coding agent they use.
4. Website generates a copyable command.
5. User runs the command in their project.
6. User asks their agent: `Use SECOD to secure this project before I keep building.`

Example for Codex:

```bash
npx skills add https://github.com/iamruzaini/secod --skill '*' -a codex
```

### 7.2 Guided stack installation

1. User selects their framework, provider, deployment target, and optional features such as payments or uploads.
2. Website resolves the transitive dependency closure for every selected skill and recommends the smallest complete set of baseline owners and framework/provider adapters.
3. The generated command must include every required dependency; a framework/provider adapter can never replace or suppress a general baseline owner.
4. User receives one command and a first-use prompt.
5. Agent detects the repository, recomputes the dependency closure and reports the security plan before making changes.
6. If a required skill is not installed or cannot be invoked, the review reports `Not verified` and cannot issue `Passed with evidence` or a launch-ready verdict.

Example for a Supabase web application with authentication and no detected payment or AI feature. The generated subset includes the complete applicable baseline dependency closure:

```bash
npx skills add https://github.com/iamruzaini/secod \
  --skill secod-core \
  --skill secod-threat-model \
  --skill secod-identity-access \
  --skill secod-web-app-security \
  --skill secod-inputs-apis \
  --skill secod-crypto-data-protection \
  --skill secod-data-files \
  --skill secod-abuse-limits \
  --skill secod-secrets-config \
  --skill secod-packages-delivery \
  --skill secod-vulnerability-management \
  --skill secod-observability-response \
  --skill secod-supabase \
  --skill secod-ship-check \
  -a codex
```

### 7.3 Pre-launch review

1. User asks: `Run SECOD ship check before launch.`
2. Agent inventories the project and relevant evidence.
3. Agent verifies applicable controls.
4. Agent returns a prioritized report with one status per item:
   - Do not ship
   - Fix before launch
   - Recommended hardening
   - Passed with evidence
   - Not verified
5. User fixes issues and reruns the check.

## 9. Skill design standards

Every skill must use the same portable structure:

```text
skills/<skill-name>/
├── SKILL.md
├── agents/
│   └── openai.yaml
├── references/
├── scripts/
└── assets/                 # Only when genuinely needed
```

### 9.1 `SKILL.md` requirements

- Folder name and frontmatter `name` must match exactly.
- Use only portable required frontmatter fields: `name` and `description`.
- Use direct, imperative instructions.
- Keep the body under 500 lines and preferably under 5,000 tokens.
- State expected inputs, process, output format, verification steps, and safe failure behavior.
- Include `Control requirements`, `Stack signals and applicability`, `Evidence to inspect`, `Negative fixtures and tests`, `Verification commands`, `Ship Check status rules`, and `References` sections.
- Put detailed provider material and edge cases in `references/`.
- Do not contain marketing, sponsorship, credentials, personal data, or long tutorial material.

### 9.2 References

- Store only material that the skill needs to carry out its job.
- Keep reference files one level below `SKILL.md`.
- Include a table of contents in reference files longer than 100 lines.
- Use official provider documentation as the primary source for provider controls.
- Map applicable portable controls to the stable [OWASP ASVS 5.0.0](https://github.com/OWASP/ASVS/tree/v5.0.0) release using version-qualified requirement identifiers, and to [OWASP API Security Top 10 2023](https://owasp.org/API-Security/editions/2023/en/0x11-t10/), relevant [OWASP Cheat Sheets](https://cheatsheetseries.owasp.org/) and the [OWASP Top 10 for LLM Applications 2025](https://genai.owasp.org/llm-top-10/) only where applicable to an AI-enabled application.
- Treat [OWASP A10:2025 Mishandling of Exceptional Conditions](https://owasp.org/Top10/2025/A10_2025-Mishandling_of_Exceptional_Conditions/) as a required source for fail-closed behavior, rollback, resource cleanup and exceptional-condition tests.
- For every framework/provider adapter, use the framework or provider's direct official documentation and official `llms.txt` or `llms-full.txt` index where published. An LLM documentation export is a discovery and snapshot aid, not sufficient authority for a security-critical claim; validate each such claim against its directly linked primary documentation.
- Record, for every security-critical source: direct URL, official documentation-index URL, document or API version, SDK version where relevant, reviewed date, content hash or ETag where obtainable, plan/tier, region, feature maturity and the exact SECOD control IDs it supports.
- Define a review-expiry date and owner. If a monitored security-critical page, API version or provider contract changes, mark the affected evidence stale and `Not verified` until the adapter is reviewed and its fixtures pass again.
- Never silently reuse a requirement across providers merely because their SDKs or webhook envelopes look similar; maintain provider capability matrices and source each capability independently.

### 9.3 Scripts

Use scripts only where deterministic checks improve reliability, for example:

- Detect likely secret exposure in tracked files and client bundles.
- Identify known provider configuration files.
- Check policy/configuration files for high-risk open defaults.
- Inventory routes, webhooks, package manifests, CI workflows, provider SDKs, and provider configuration.
- Produce machine-readable evidence for `secod-ship-check`.

Scripts must be safe by default, read-only unless the user explicitly asks for a change, and must never transmit project content or credentials to an external service without explicit approval.

Every script must additionally:

- Disable network access by default and declare any optional network destination and transmitted fields before requesting approval.
- Treat repository paths, filenames, symlinks, archives, configuration values and command output as untrusted input; prevent traversal outside the inspected root and never follow a symlink into an unapproved location.
- Avoid shell-string interpolation of repository-controlled values; use argument arrays or equivalent safe process APIs.
- Use securely created temporary directories, deterministic cleanup and explicit file-count, byte, memory, process and execution-time limits.
- Redact credentials, bearer tokens, cookies, authorization headers, request/response bodies, prompts and private user data from stdout, machine-readable evidence and error output.
- Pin or integrity-verify runtime dependencies and fail closed when a required parser, scanner or runtime is missing or incompatible.
- Have negative fixtures for malicious filenames, symlinks, archives, command-like values, oversized input, timeouts and interrupted cleanup.
